# Feature-owned modules

Foundation supports Home Manager on x86_64-linux. The root `flake.nix` is generated by flake-file; its only output expression runs flake-parts over `import-tree ./modules`.

| Directory | Responsibility |
| --- | --- |
| `modules/flake/` | Framework inputs, pure discovery, public exports and templates |
| `modules/home/` | Home construction, identity, startup, commands and activation |
| `modules/profiles/` | Schemas, catalogs, generation, editing and migration previews |
| `modules/apps/` | Application metadata, settings and package recipes |
| `modules/roles/` | Professional and Personal presets |
| `modules/capabilities/` | Optional groups and ordered application dependencies |
| `modules/hosts/` | Machine, CPU, GPU and model aspects |
| `modules/providers/` | Package sources, Homebrew, Flatpak and graphics |
| `modules/ci/` | Profile cases, dependency graph and generated-file checks |

Each feature has a path-derived ID, a public `default.nix` flake-parts module, and a private `_feature.nix` descriptor. Some framework features register in `registration.nix` alongside their existing module. Private Home Manager modules, functions and `_assets/` are excluded from import-tree. The empty `modules/local.nix` remains a compatible consumer customization module and is also a valid empty flake-parts module.

Discovery registers available descriptors without activating them. The pure loader validates IDs, missing dependencies and cycles for both supported schemas. Metadata remains separate from lazy configuration functions, so JSON/YAML generation and catalog projections need neither a complete flake evaluation nor Nixpkgs. Existing `lib/` entry points forward to their owning feature; constructor arguments and exported aspect aliases remain compatible.

`dependencies` and `schemaDependencies` are ordered lists. Both Den includes and CI traversal consume them. Profile roots come from `profiles/composition/_selection.nix`; application/capability/role catalogs project the same declarations. A Home Manager assertion compares actual imported Den feature IDs with the declared closure. Shared applications activate once. Explicit package ordering preserves legacy composition, and startup hooks retain their `mkBefore` order. Activation DAG edges remain defined in their owning modules.

To add a feature, add its descriptor and public registration module, then declare dependencies beside the feature that needs it. No central application or role list needs editing. Put input declarations in that feature's public module as `flake-file.inputs`. Run:

```sh
nix run path:.#write-flake
nix run path:.#write-ci-graph
nix develop path:.#ci --command bash tests/ci.sh
bash tests/nix-check.sh
```

The pinned flake-file workflow is documented at https://flake-file.denful.dev/. Lock pruning is disabled. Existing Den and package revisions were retained; flake-parts and import-tree were promoted from the lock, and flake-file starts at `619d2212`.

Dependency automation edits `modules/flake/framework/default.nix` for Den's tested gen revision, regenerates the root flake and graph, and includes module sources and generated artifacts in its review PR. Consumers still own `profile.json`, `customize.nix` and `modules/local.nix`. This refactor does not activate a profile or change Finite's pin.
